## 1. 给项目负责人的说明

后续由 Codex 负责代码、测试、构建、缺陷修复和开发记录。PRD 说明“做什么、怎样才算合格”，这份计划是 Codex 每次开始或继续开发时的执行依据。你主要负责体验产品，并在需要真实设备、付费资源或公开发布时参与。

用户已明确最终目标：界面与功能和Mac原版基本相同，并根据窗口大小适配。先用原型证明图片合成、笔刷和保存，然后完成基础版本，再继续原版功能与界面对齐。基础P0完成只是中间里程碑。

以前按人工团队估算的4–6个月和人月费用，不再作为本项目的交付计划。Codex 的进度取决于可用工具、运行环境、构建结果和真机反馈，不能把人工工期简单换算成AI工期。

改为按可检查的里程碑推进：每次完成一段能验证的工作，记录证据和下一步。首次可构建原型完成后，再根据实际进度给出近期估算；不预先保证整个项目在某天完成。

本次v0.4更新把最终原版对齐设为已授权目标，PRD第21节是最终验收依据。P1/P2里的原版功能不再是可选项；新增的非原版增强仍需单独判断。目前已建立只读预览原型，实际进度见第15节；基础编辑、保存与导出链路尚未贯通。

## 3. 技术方案，用通俗的话说明

### 3.1 建议架构

把应用分成四部分，便于维护：

1. **界面**：按钮、工具栏、图层面板，用 Kotlin 和 Jetpack Compose 开发。
2. **编辑规则**：图层数据、操作记录、撤销和资源限制；不要把这些规则散落在按钮代码里。
3. **图像核心**：用 C/C++ 保留和迁移像素算法，通过 Android NDK 编译；像素缓冲由核心集中管理，避免跨界面传输整张大图片。
4. **图像显示**：专门的 GPU 画布负责合成与笔刷，不依赖普通界面控件逐帧重画所有像素。

Kotlin 是安卓常用开发语言，NDK 是把 C/C++ 代码编译成安卓可用程序的工具。

核心应为文件保存、缩略图、画布预览和最终导出提供一致的图层规则。平台调用放在边界，尽量避免未来再次被某一种系统接口绑住。

### 3.2 GPU 后端选择

- 原型优先比较 OpenGL ES 3.1 和 Vulkan 的实际可行性。
- OpenGL ES 通常更容易较快完成基本实现；Vulkan 提供更多资源控制，但开发和驱动排查成本较高。
- 本项目有计算型笔刷，原型必须覆盖计算能力、内存同步与不同 GPU 驱动。
- Codex 先以 OpenGL ES 3.1 作为可撤回的原型选择，记录原因；根据实测结果决定保留还是切换 Vulkan。没有真机时标为待验证，不将临时选择写成已验证结论。
- 首版先保留关键 C 算法的参考实现，方便判断 GPU 输出是否正确；不因此承诺所有设备都能用 CPU 流畅运行完整编辑器。

### 3.3 复用清单

| 现有内容 | 做法 |
| --- | --- |
| 图层与变换模型 | 沿用规则，改成与安卓界面和 Apple 图像类型分离的模型 |
| C 像素算法 | 逐文件接入 NDK，用固定素材验证输出 |
| DitherPixels.c | 替换 Apple 的 dispatch 和 Blocks 并行写法，首版不依赖此功能 |
| HealPixels.c | 处理 M_PI 等编译兼容问题，后续修复工具阶段使用 |
| Metal shader | 移植计算逻辑，重写资源绑定和同步，不能直接拿到安卓编译 |
| Core Image/Core Graphics | 替换成安卓或自有图像处理路径，逐项验证 |
| SwiftUI/AppKit 界面 | 重写，并重新设计触屏入口 |
| Apple Vision | P2 选择替代模型 |
| `.comp` 格式 | 基础字段保持兼容，增加安卓 ZIP 交换包装 |
| Mac 测试 | 转成安卓/C 核心的行为测试和固定素材，不能直接运行原测试目标 |

当前已做的 Linux 编译初查只有“9 个 C 文件中 7 个能生成目标文件”。这不是 Android ARM64 编译成功，也不是算法结果已验证。

## 4. 环境与设备准备

### 4.1 正式开发环境

- Codex 可用Linux命令行环境，无需安装图形界面的Android Studio；人工使用时仍可用Android Studio。大型构建推荐32GB内存和充足SSD空间。
- 完整 JDK、Android命令行SDK、NDK、CMake、Git；Gradle通过项目固定版本的Wrapper运行。
- 固定 Gradle、安卓构建插件、NDK 和依赖版本。
- 一台支持笔压的安卓平板、一台目标折叠屏；尽量覆盖 Adreno 与 Mali GPU。
- 一台较低配置设备用于检查资源限制和降级行为。
- 可访问的Mac原版环境，用于生成基准导出和格式往返验证。没有时先做格式与固定素材检查，视觉对照明确记为待测。
- CI 自动构建环境。CI 是每次代码提交后自动编译和检查的服务。

### 4.2 当前聊天环境

当前是 Linux，实际资源约 2 核 CPU、8 GB 内存、剩余约 30 GB；已有 Git、GCC 和 Java 运行环境，缺少完整安卓工具链，也未提供真机、GPU 和硬件虚拟化设备。

可以在此进行文档、代码抽离、项目搭建和工具链安装后的轻量构建。大型构建可能受资源限制，真机图形、笔输入、发热和 Mac 对照测试必须安排外部环境。

原型阶段先确认工具链安装空间和网络条件；不足时使用独立构建机器或 CI。不能把“代码已经写好”当成“设备上已经跑通”。

## 5. 阶段计划与里程碑

阶段按依赖推进，不按固定周数承诺。可以继续不受阻塞影响的工作，但不能跳过已阻塞的验收，把阶段标记为完成。

| 阶段 | 推进顺序 | 主要产出 | 通过条件 |
| --- | --- | --- | --- |
| A：构建准备 | 首先进行 | 工具版本、首版清单、草图、空项目与构建检查 | Debug APK构建成功；安装验证单列，等待设备不阻塞核心工作 |
| B：贯通原型 | A的构建基础完成后 | 合成、变换、分块笔刷、最小撤销、保存重开、导出 | 自动检查通过；真机链路与性能另列，未测时阶段不能完整验收 |
| C：P0核心完善 | 贯通基础链路后 | 完整首版图层/笔刷/撤销、导入导出、混合一致性 | 相关PRD要求有实现与测试证据，无假功能入口 |
| D：设备与文件适配 | 核心稳定后，也可提前做不依赖GPU的部分 | 自适应布局、折叠切换、笔压、恢复、ZIP交换 | 设备场景和基础Mac往返实测通过 |
| E：稳定性与用户试用 | C/D功能实现后 | 低资源测试、修复、5人试用记录、支持名单 | 无关键数据丢失问题，性能达到冻结门槛 |
| F：测试交付 | 候选版本通过后 | 安装包、版本说明、使用说明、升级说明 | 独立安装与核心操作通过；公开发布按明确指令执行 |
| G：核心原版对齐 | 基础测试版本完成后 | 选区、蒙版、分组、完整混合、文字/形状/渐变、调整与工作区 | 对应MAC细分项和原版操作检查通过 |
| H：复杂原版对齐 | 核心语义稳定后 | 图层效果、完整滤镜、修复/填充、RAW、PSD/PSB、智能能力、完整文件语义 | 输出、模型效果、格式与任务恢复检查通过 |
| I：最终界面与功能验收 | 原版清单实现后 | 宽/中/窄截图对照、典型作品流程、完整差异表与设备报告 | PRD21.4通过；未获接受的例外不得记完成 |

设备测试可以积累到有设备时集中完成。等待期间继续模型、文件安全、恢复策略和自动测试，不重复询问同一个问题。GPU正确性或性能未验证时，可以做相关代码，但不能宣称原型已经通过真机验收。

### A：准备与范围冻结

任务：

- 沿用 PRD 中 P0 清单和基础文件兼容范围。机型未提供时标为待测，不阻塞构建与核心实现。
- 确定 Android 最低版本和 ARM64 构建。
- 初始化安卓目录与构建脚本，优先与现有 Mac 工程分开放置。
- 制作横屏、竖屏、折叠屏和窄窗口草图。
- 准备透明图层、照片方向、七种混合模式等素材，保留来源和使用权限记录。
- 建立缺陷表与版本命名方式。

交付：构建成功的空Debug APK、环境说明、设计草图、冻结清单、素材索引；如未有设备，安装状态明确写为待测。

### B：贯通原型，最重要的阶段

任务：

- 显示图片并完成 1/5/10 层合成、透明度和七种首版混合模式。
- 实现画布平移缩放和图层移动缩放旋转。
- 实现 256×256 分块笔刷和基本橡皮擦、单笔撤销。
- 加入真实笔事件与压力数据，不仅用模拟鼠标演示。
- 完成一个基础项目的保存—重开—导出，验证存储与渲染方案能连起来。
- 检查不同 GPU 能否使用选定后端，验证纹理尺寸限制。
- 测量 4K 场景的内存、帧耗时、笔刷同步读回开销和长时间使用退化。
- 与 Mac 的基准图比较，找出混合、透明边缘和坐标方向差异。

交付：原型 APK、演示录像、可重开的示例项目、基准报告、后端选择说明、更新后的工期。

评审决定：

- **继续**：关键链路正确，设备性能可达到或经过明确优化能够达到目标。
- **缩小**：降低画布/图层范围或减少功能，重新写清支持范围再继续。
- **暂停扩大开发**：核心渲染或保存路径仍不能稳定工作，先解决问题，不继续制作大量面板。

不能以“界面好看”代替原型通过。

### C：P0 核心完善

任务：

- 完整图层管理、缩略图与顺序调整。
- 变换的数字输入、确认取消和单次历史记录。
- 笔刷软硬程度、透明度、平滑与取色。
- 共享分块快照和受内存预算约束的历史。
- PNG/JPEG 导入方向、颜色和透明度校验。
- 预览、导出共用合成规则，支持取消与错误恢复。
- 在图像分配前检查尺寸与预算，不依靠分配失败后补救。

交付：核心功能测试包、固定素材结果、已知问题表、内存峰值报告。

### D：设备与文件适配

任务：

- 根据窗口宽度切换面板，处理软键盘遮挡和48dp点击区域。
- 双指导航、手指绘画开关、笔压、输入取消和掌触场景。
- 折叠展开、横竖屏、分屏、多窗口、进入后台的状态保留。
- 将“手动保存文件”和“内部恢复副本”分开管理。
- 实现恢复副本轮换、失败保护、缓存清理。
- 通过系统文件接口保存和打开，处理权限失效及远端提供方限制。
- ZIP 安全检查、Mac 基础项目预检和双向交换说明。

交付：适配测试包、恢复测试报告、Mac 文件往返样例、文件操作说明。

### E：稳定性和试用

任务：

- 跑完整测试矩阵，重点检查保存、恢复、变换后绘画和导出。
- 加入强制结束、低存储、超大输入、权限取消的失败演练。
- 连续使用30分钟以上，记录性能退化和温度。
- 组织5位非开发用户试用，修复主要操作困惑。
- 确定正式机型、画布与图层范围。
- 关闭或清楚标注未完成功能入口，不留下能进入但无法完成的流程。

交付：候选版本、测试报告、支持名单、用户试用结果。

### F：测试发布

任务：

- 创建正式签名流程和密钥备份，构建可安装包。
- 测试干净安装与上个测试版升级，检查项目和恢复副本兼容。
- 准备使用说明、已知问题、隐私说明和第三方声明。
- 由没有参与编译的人按说明安装和完成核心任务。
- 发布给测试用户，收集明确复现步骤，修复严重问题。

交付：签名 APK；如确定商店发布，再准备 AAB、商店资料与政策检查。公开上架时间不包含在首版研发估算内。

## 7. 测试与验收方法

### 7.1 自动检查

- 每次代码提交自动编译安卓工程和图像核心。
- 图层顺序、坐标变换、预算计算、文件预检、撤销分支进行行为测试。
- 分块笔刷跨边界、交叉、重复更新、提交快照和下一笔连续操作进行像素测试。
- 固定样例验证保存—重开元数据与像素，损坏文件不替换当前项目。
- PRD第19节的FR/TC编号作为追踪依据。每个工作包标注适用用例；P1用例不混入P0通过率。
- RECOVERY-01完成至少200次可重复的内部保存故障注入，记录中断阶段、旧/新版本和恢复结果；外部提供方另测。
- FILE-01准备至少20种基础特性组合，固定Mac源码版本并进行格式与像素检查；Mac运行结果没有证据时保留待测。
- 预览与导出对照采用有记录的误差规则；随机噪声等后续功能固定种子。
- 不给每个按钮写重复实现的测试，把重点放在数据正确性和高风险边界。

### 7.2 真机矩阵

| 维度 | 必须覆盖 |
| --- | --- |
| 设备 | 笔平板、折叠屏，尽量有Adreno/Mali两类GPU |
| 内存 | 12GB基准、8GB补充；实际安全预算单独测量 |
| 窗口 | 横屏、竖屏、分屏、内屏展开、外屏窄界面 |
| 输入 | 手指、双指、笔、笔压开关、掌触、输入取消 |
| 图片 | 透明PNG、照片方向、损坏文件、超范围图片 |
| 工程 | 空文档、1/5/10层、隐藏层、各混合模式、不支持的Mac字段 |
| 存储 | 本地文件、选定的外部文件提供方、权限取消、空间不足 |
| 生命周期 | 返回桌面、锁屏、旋转、折叠、进程被回收、版本升级 |

模拟器用于布局和基本流程，不能替代 GPU、笔输入、发热和真机恢复测试。

ADAPT-01在基准折叠设备进行至少50轮形态切换，按PRD第17节区分已完成工作、活动笔画和输入取消。GPU Surface销毁/重建不得重复提交笔画。没有设备时写出脚本与步骤，但不记为真机检查通过。

### 7.3 项目负责人能亲自检查的流程

1. 安装Codex构建的测试包，打开新建页面。
2. 导入两张照片，把其中一张缩小、旋转、调透明度。
3. 新建空白图层，画几笔，撤销和重做。
4. 保存项目，退出并重开，查看各图层是否还在。
5. 导出 PNG/JPEG，在系统图片查看器中打开。
6. 编辑后等待自动保存，结束应用，再启动检查恢复。
7. 切换横竖屏或折叠展开，检查内容与选中图层。
8. 尝试导入不支持的项目，检查是否清楚提示并保护当前作品。

每次验收保留版本号、设备、问题描述和截图/录像。开发人员的“本机能跑”不能代替这些记录。

## 13. Codex执行规则

### 13.1 开始与接续

每次开发按下面顺序执行：

1. 阅读仓库及目标目录的`AGENTS.md`、PRD、本计划第14–15节，查看Git状态；保留用户已有改动。
2. 检查实际工具与资源，不把上一次的环境检查当作本次工具一定可用的保证。
3. 根据任务依赖选择下一个可完成步骤；先检查已有代码，避免重复实现。
4. 完成代码、必要检查、结果记录，再汇报。失败先定位修复，不用反复跑同样命令冒充进度。
5. 遇到单项阻塞，记录原因并继续其他独立任务；只有缺少的信息确实影响后续决定才询问。

你可以用一句话接续：“按开发计划继续安卓版，先读进度记录，完成下一个可验证任务。”新聊天仍需能访问同一仓库；没有仓库时不能仅凭聊天复原代码。

### 13.2 代码边界

- 安卓代码放在仓库根目录的`android/`，不重排现有Mac工程。
- 建议`android/app/`放界面、平台文件与生命周期代码，`android/editor-core/`放可独立检查的编辑模型，`android/native/`放C/C++与JNI接口。JNI是Kotlin与C/C++之间的连接层。
- 在确有需要前不拆过多模块。GPU画布先放app内清晰的包，后续按依赖抽离。
- 固定窗口、画布、图层原始像素三类坐标，以及8-bit RGBA/sRGB、通道顺序、预乘Alpha和行步长；CPU、GPU、文件读写共享规则。安卓内部会话字段独立保存，不直接扩充Mac manifest。
- 初期通过构建配置引用可移植C文件；兼容修复优先放安卓层。确需修改Mac共用文件时，记录影响并做相应检查。
- 不为安卓添加功能而改变Mac工程或原文件格式；格式确需变化时遵守仓库版本规则和往返测试。
- 用户聊天与说明用通俗中文，源码和首版UI沿用仓库英文约定。
- 不默认增加账号、服务器、收费、追踪或原版之外的产品功能。PRD第21节原版对齐清单已获用户授权，P1/P2表示推进顺序而非可选范围。

### 13.3 自动检查命令

构建准备完成后，固定以下入口；实现时若改动模块名，需要同步改写本节。

| 检查 | 在`android/`目录执行 | 作用 |
| --- | --- | --- |
| 编译安装包 | `./gradlew :app:assembleDebug` | 包含ARM64原生部分的Debug APK构建 |
| 核心规则 | `./gradlew :editor-core:testDebugUnitTest`（添加模型用例后）；应用规则使用 `:app:testDebugUnitTest` | `editor-core`是纯Kotlin源码的Android library模块；当前没有新增模型或像素测试 |
| 安卓本地测试 | `./gradlew :app:testDebugUnitTest` | 不依赖设备的应用逻辑检查 |
| 静态检查 | `./gradlew :app:lintDebug` | 查常见安卓代码与资源问题 |
| 设备检查 | `./gradlew :app:connectedDebugAndroidTest` | 已连接设备上的功能检查 |

目前已有 `:editor-core` 纯Kotlin模型模块及单测、app规则/生产文件管线/生命周期单测，以及 `android/native/` 下的NDK ARM64入口；`:app:assembleDebug` 已实际编译并打包 `arm64-v8a/libcompositor_editor.so`。本轮已加入PNG完整性/像素、固定预算和历史检查，最终实际统计见15.0与修复验证；JNI固定像素输出仍待检查。`connectedDebugAndroidTest`仍无测试实现和连接设备；新增模型测试后运行 `:editor-core:testDebugUnitTest`，C算法像素检查仍需独立入口。

首次构建验证Gradle Wrapper来源与完整性，固定SDK、NDK、JDK和插件版本；禁止将本地SDK绝对路径、账号密码或签名密钥提交到仓库。云环境优先单构建任务，监控剩余磁盘，不盲目下载模拟器镜像。

工具下载或访问失败时，记录实际错误和替代方案；未检查的代码不能写成“构建通过”。CI仅在有可用配置与授权资源时启用，不能以编写了配置文件冒充CI已运行。

### 13.4 完成标准与证据

每项工作分开记录：

- **未开始**：还没有实现。
- **开发中**：代码不完整或存在已知失败。
- **实现完成／自动检查通过／设备待测**：分别填写，不把不同层级合并。
- **阻塞**：写明缺少资源或失败原因、恢复条件和可继续的其他任务。
- **已验收**：所有适用验收条件通过，并有实际证据。

无操作效果的按钮、固定返回成功的保存、只显示演示图片的画布、未接入的笔压，都不能算功能完成。自动检查通过也不能代表真机GPU和手写笔验证通过。

每条证据至少记录：代码版本（提交ID或工作区状态）、环境/机型、运行命令或操作步骤、实际结果、报告/产物位置。必要日志和素材放在`android/validation/`，大型产物不提交仓库；外部报告不可用或临时文件过期时，应能按记录重新生成。

发布前补齐所有P0验收项。新问题优先处理数据丢失、保存损坏、崩溃和核心流程错误，再处理性能和外观。

### 13.5 默认决定与需参与事项

Codex自行完成：目录结构、依赖版本、普通界面细节、算法移植、可撤回的架构选择、修复与必要测试，记录重要决定即可。

涉及PRD重大范围缩减或新增原版之外的功能时，先给出具体方案和影响，请你决定；不能悄悄删除P0或MAC清单项。继续原版对齐无需再次请求开发授权。无法真机验收时标为待测，不通过降低要求宣称完成。

新增付费、公开上架、上传用户项目到外部服务、破坏性删除或覆盖用户数据，在没有明确授权时需要你的决定。需要时先准备可审查的具体结果，不把日常开发变成不断确认。
